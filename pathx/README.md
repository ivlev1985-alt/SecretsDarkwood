# PathX — Path Explorer

Автономная утилита-просмотрщик для проекта **SecretsDarkwood**.
Живёт в папке `pathx/`, работает на GitHub Pages, **не требует сборки и дампов**.

> ⚠️ **Если ты ИИ-агент или разработчик:** прежде чем что-либо менять в этой
> папке или рядом с ней — прочитай этот файл целиком. Здесь зафиксированы
> правила, нарушение которых ломает либо утилиту, либо игру.

---

## 1. Суть утилиты

PathX показывает **все визуальные сущности игры** в одном интерфейсе:

- **процедурные модельки** — маг-герой, скелет-лучник, огненный шар,
  магический снаряд, тайная нова, цепная молния, кольцо холода, смерч,
  огненная стена (рендереры из `js/render/` и `js/systems/`);
- **спрайтовые сущности** — монстры, пропы, сундуки, лут, эффекты,
  питомцы, иконки (берутся из `config/*.json` и `assets/`).

Для каждой сущности доступны: переключение состояний (idle/walk/cast/death…),
направлений, слайдеры параметров конфига, воспроизведение анимации с
регулировкой скорости и прокруткой по времени.

Назначение: быстрая визуальная отладка «как выглядит и анимируется» без
запуска игры, без ботов, без боя.

## 2. Структура папки

| Файл | Назначение |
|---|---|
| `README.md` | Этот файл. Источник истины по архитектуре утилиты. |
| `index.html` | Всё приложение: UI, загрузка конфигов/ассетов, цикл анимации. CSS и JS встроены (inline) — файл самодостаточен. |
| `manifest.js` | Реестр процедурных моделек: какой рендерер, откуда брать конфиг, как вызывать `draw()`, какие состояния/направления/зум (`extent`) у модели. |
| `adapters.js` | Фабрики «поддельных» сущностей (`makeHero`, `makeFireball`, `makeFrostRing`, …), симуляция времени (`stepEntity`) и собственная отрисовка молнии. |
| `style.css` | Историческая копия стилей (в текущей версии CSS инлайнится в `index.html`; файл держится как справочник). |

## 3. Главные принципы

### 3.1. Жёсткая независимость игры от утилиты

Это **самое важное правило**.

- Игра (`index.html` в корне, `js/`, `config/`, `assets/`) **ничего не знает**
  о существовании `pathx/`. В коде игры нет ни одного импорта, упоминания
  или ссылки на PathX.
- Зависимость **однонаправленная**: PathX → игра. Утилита импортирует
  рендереры игры «как есть» через `import('../js/render/...')` и читает
  `../config/*.json` и `../assets/*` по HTTP.
- **Запрещено** менять код игры, конфиги или ассеты ради нужд утилиты:
  никаких «поправил рендерер, чтобы в PathX работало», никаких новых полей
  в конфиги «для превью», никаких экспорт-хуков.
- Все костыли, обёртки и адаптации живут **только внутри `pathx/`**
  (см. §4). Если рендерер игры неудобен — адаптирует адаптер, а не рендерер.
- Утилита **только читает** файлы игры. Ни одна её правка не должна
  затрагивать файлы вне `pathx/`.
- Следствие: напарник может свободно рефакторить игру агентами — PathX
  либо продолжит работать, либо честно покажет ошибку в конкретной
  карточке (обёрнут `try/catch`), но игра от него не сломается никогда.

### 3.2. Рендереры вызываются без моков игрового рантайма

PathX не поднимает `Game`, `SkillSystem` (кроме молнии, см. §4.6), камеры и
т.д. Каждому рендереру подсунуты минимальные «подделки» сущностей из
`adapters.js`, содержащие ровно те поля, которые `draw()` реально читает.

### 3.3. Конфиги — те же, что у игры

Читаются `../config/*.json` с той же обработкой: из текста вырезаются
комментарии `//` и `/* */` (сканер с учётом строк), затем `JSON.parse`.
Пути ассетов в конфигах относительны корня игры (`./assets/...`), утилита
догружает их как `../assets/...`.

### 3.4. Ничего не хранится

Утилита stateless: нет localStorage, сейвов, куки. Обновил страницу — чистый
старт. Можно деплоить как есть на GitHub Pages из подпапки `pathx/`.

## 4. Известные особенности рендереров игры (почему адаптеры такие сложные)

Эти пункты — результат разбора исходников `js/render/`. Они **не баги игры**,
а её штатное поведение, которое утилита воспроизводит/обходит на своей стороне:

1. **`MagicProjectileRenderer`** читает конфиг как `this.visuals[p.weaponId]`.
   Поэтому в конструктор передаётся обёртка `{ magic_bolt: cfg }` и т.п.
   (`ctor: 'visuals'` + `visualKey` в манифесте).
2. **`FireWallRenderer`** читает `this.visuals.fire_wall` — та же обёртка.
3. **`HeroMageRenderer` / `SkeletonArcherRenderer`** кэшируют позу по
   `cfg.cache_fps`. `cache_fps: 0` давать **нельзя** — квантование `qf/fps`
   даст `NaN`. В манифесте стоит `force: { cache_fps: 240 }`: кэш обновляется
   каждый кадр, анимация идёт плавно в реальном времени.
4. **`FireballRenderer`** при `mode !== 'always'` зовёт `assets.isMissing()`.
   Утилита форсирует `mode: 'always'` — процедурная отрисовка работает без
   ассет-менеджера.
5. **`FrostRingRenderer.draw(ctx, weapons, time, assets)`** ждёт `Map` вида
   `id -> { active, level, cfg, orbs, orbSpin, player }`, где `cfg` — конфиг
   **оружия** из `skills_config` (не visuals-секция!). Угол орбит снаружи
   двигает `SkillSystem` — в утилите это делает `stepEntity`.
6. **Цепную молнию** рисует не рендерер снаряда, а `SkillSystem.drawLightning`
   по массиву `lightningFx`. Чтобы не тянуть в браузер весь `SkillSystem`
   (он импортирует `Projectile`, `Pool`, `CombatSystem`…), `adapters.js`
   содержит `makeLightningScene` — порт того же прохода отрисовки по тем же
   полям `game_config.visuals.lightning_chain`. **Если формат молнии в игре
   изменится — синхронизируй порт вручную** (это единственное место-дубликат).
7. **`TornadoRenderer`** кэширует кадр по `visual.cache_fps` — так же
   завышается до 240 через `force`.
8. **`HeroMageRenderer` / `SkeletonArcherRenderer`** принимают 4-м аргументом
   не `assets`, а `opts = { scale, w, h }`. Им утилита передаёт зум-масштаб,
   остальные рендереры получают `assets = null` (при `mode: 'always'` он не
   используется).

## 5. Как добавить новую модельку

**Процедурную:** добавить запись в `PROCEDURAL` (`manifest.js`) — указать
модуль, класс, источник конфига (`cfgFile`/`cfgPath`, опц. `cfgPick`/`cfgSub`),
способ вызова (`draw: 'entity' | 'weapons' | 'skill'`, `ctor: 'section' |
'visuals'`), фабрику сущности (`entity`), зум (`extent`), состояния и
направления. При необходимости — новую фабрику в `adapters.js` и ветку в
`makeEntity()` внутри `index.html`.

**Спрайтовую:** как правило ничего не нужно — записи для монстров, пропов,
сундуков, лута, эффектов, питомцев и иконок генерируются автоматически из
конфигов при загрузке.

## 6. Запуск

```bash
# из корня репозитория (любой статический сервер, ES-модули требуют http://)
npx http-server -p 8080
# открыть http://localhost:8080/pathx/
```

На GitHub Pages утилита доступна по `https://<user>.github.io/<repo>/pathx/`,
если репозиторий публикуется целиком.

## 7. Правила для ИИ-агентов (сжатая выжимка)

1. Сначала прочитай этот README, потом код.
2. Правки — **только внутри `pathx/`**. Файлы игры — read-only.
3. Не ломай однонаправленность: игра не должна узнать о PathX.
4. Особенности API рендереров (§4) обходятся адаптерами, а не правками
   рендереров.
5. После правки — проверь загрузку страницы через локальный http-сервер и
   консоль браузера; каждая карточка изолирована `try/catch`, падение одной
   модели не должно ронять утилиту.
6. `makeLightningScene` в `adapters.js` — порт логики `SkillSystem`; при
   изменении молнии в игре обнови порт.
